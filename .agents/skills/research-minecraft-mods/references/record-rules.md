# Record rules (load only when needed)

`new` creates a single `{revision:0,family:…}` work file. `checkout` saves the current entry in the same format. `upload` also accepts `{entries:[…]}` with up to 20 families (for example a catalogue export). Existing revisions must be current. It does not rewrite the work file after saving; checkout fresh for a later edit. Repeating an unchanged upload is a no-op.

Use `template TYPE` for exact object fields. Patch file keys are JSON pointers relative to **family**, e.g. `{"/description":"…","/projects/0/description":"…","/evidence/-":{…}}`. `/array/-` appends one item; `/array/0` replaces one; `/array` replaces all. Unmentioned fields remain intact. Lists and objects remain in the file; only changed field paths print. `show FILE --pointer PATH` prints just that subtree. An omitted pointer prints only IDs, state, revision, and counts.

- Family/project IDs: lowercase ASCII letters/digits/hyphens/underscores, max 100 characters. Saved project IDs cannot be removed or reassigned. A new scaffold starts with one project whose ID matches the family ID; adjust unsaved IDs when needed. New projects from `template project` need their own unique ID and researched name/description.
- All lists are present (`[]` if empty). URLs use HTTPS without credentials. Dates: `YYYY-MM-DD`; release publication time: ISO instant, e.g. `2026-10-22T12:00:00Z`. No evidence URLs are fetched by the client/server.
- Listing platforms: CURSEFORGE or MODRINTH; project IDs and URLs must refer to the same real platform listing. Distinct projects may not share one platform project ID.
- Support: exact numeric Minecraft version and loader FORGE/NEOFORGE/FABRIC/QUILT. Availability UNKNOWN/RELEASED/ANNOUNCED/NO_BUILD_FOUND; maintenance UNKNOWN/ACTIVE/FIXES_ONLY/DISCONTINUED. Any non-UNKNOWN claim needs checkedAt and evidenceIds. The user does not want exact mod-release versions persisted: leave releases empty and cite the checked release index/file page as evidence of availability.
- Evidence has family-local ID, URL, specific claim, summary, checkedAt, uncertain. References are family-local evidence IDs; one availability source is not automatically proof of parity.
- Relationships need relatedProjectId, type, optional target (null means all versions), notes, evidenceIds. Types: REQUIRED_DEPENDENCY/OPTIONAL_DEPENDENCY/ADDON/FORK/SUCCESSOR/ALTERNATIVE/LOADER_EQUIVALENT/INCOMPATIBILITY. Related project must already exist or be in the same upload. Scoped target must match a support record of the source project.
- INCOMPATIBILITY additionally requires nonblank scope/failure notes and at least one non-uncertain source. It appears from both affected family detail pages; store a single relationship per scope instead of mirrored duplicates. State whether the warning is a current metadata declaration, maintainer report, conditional setting, or local reproduction. No recorded conflict is not proof of compatibility.
- Comparisons name left/right branches: projectId plus target. Both must be support records in this family. Parity UNKNOWN/EQUIVALENT/PARTIAL/DIVERGENT; non-UNKNOWN needs checkedAt and evidenceIds. Keep concrete differences in notes.

The upload command reports committed=true if a save succeeded but readback failed or changed concurrently. Preserve the same file and rerun to check current state; do not invent another create. A revision conflict requires a fresh checkout and reconciliation. Full server validation remains authoritative.
