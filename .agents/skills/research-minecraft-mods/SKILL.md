# Research requested mods

Work from the Webserver repository root. Use `py scripts/mod_research.py`; it prints compact JSON and keeps full records in files. Do not dump the database or reload the long API guide for routine work.

1. Run `status`, then `find "requested name"` (includes drafts/archives). Read the user's requested mods, versions, themes, and scope; use primary Forge 1.20.1 / NeoForge 1.21.1 plus historical Forge 1.7.10 / 1.12.2 when no narrower targets were requested. Future 26.x/27.x are watch categories, not downloadable support claims.
2. `checkout family-id --out build/mod-research/job.json` for an existing family; otherwise `new family-id --name "Name" --out build/mod-research/job.json`. Use unique filenames per job. Existing entries must be checked out fresh; preserve unrelated fields and distinct originals/forks/revivals. Search aliases and related names before creating duplicates.
3. Research current official listings, release files, maintainer documentation/repositories, and changelogs. Record source URL, supported claim, finding, check date, and uncertainty. Verify Minecraft version **and** loader, but do not persist exact mod-release versions (user preference). Released means a verified downloadable build, documented by dated evidence; `releases:[]` is valid. Dates/version numbers do not prove maintenance or parity. Keep unverified findings UNKNOWN; no-build-found requires a recorded search, not a failed request. Never reuse synthetic examples as research. Record maintainer-confirmed incompatibilities as INCOMPATIBILITY relationships with scope, concrete conditions, and verified sources; do not label already-fixed issues or generic unsupported combinations as universal conflicts.
4. Update the working file directly, or write a small pointer patch and run `patch job.json --changes patch.json`. Read only needed fields with `show job.json --pointer /projects/0/support`; use `template evidence` (or support/project/listing/relationship/comparison/release) rather than inventing JSON shapes. See [record rules](references/record-rules.md) only when filling those structures. Attach evidence IDs to support, relationships, and parity claims. New records default to drafts; publish when the user's request calls for public entries, and preserve existing publication state otherwise.
5. Run `upload job.json --reason "Researched … per user request"`. This single command checks revisions, skips unchanged families, validates transactionally, saves, and reads back. Report only changed IDs/revisions and meaningful uncertainty. On conflict, checkout to a new file, reconcile, and retry; do not force revisions. On connection/token failure, retain the research file and report the missing connection without claiming it was uploaded. No direct SQLite writes or deployment as a workaround.

The Raspberry Pi is the authoritative catalogue for future requested updates (user preference). Run the client without connection overrides: its Windows-user-encrypted saved connection opens an automatic localhost SSH tunnel to `pi@pi` and authenticates to the Pi loopback API. `status` should show localhost port 19081, mapped to Pi port 8081. Never silently fall back to a local database when the Pi is unreachable: retain the research file and report the connection issue. Credentials are stored outside the repo under the current user's local app-data directory; never print/store them in research files. Explicit `MODS_API_BASE`/`--base` plus environment credentials are for intentional isolated tests only. No recurring schedules, unrelated research, or public network exposure are authorized by this skill.
